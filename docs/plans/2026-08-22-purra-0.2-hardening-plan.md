# PurrA 0.2 Fail-Closed Hardening Plan

- Status: Implemented and locally verified
- Date: 2026-08-22
- Target: `0.2.0`
- Baseline: `main` at `fdbada4` / `v0.1.0`
- Scope owner: PurrA Core

## 1. Objective

Make PurrA's existing fail-closed claims true at the two currently incomplete
boundaries, then reduce the change risk in the two orchestration monoliths
without changing the product-neutral ownership model.

The release is complete only when:

1. Durable continuation cannot run under an unproven Agent composition.
2. An unsupported or invalid tool schema cannot authorize a handler call.
3. Public exports are intentional and mechanically checked.
4. The Engine and Runtime orchestration paths are smaller while preserving the
   same Run, output, authorization, cancellation, recovery, and replay behavior.

## 2. Verified baseline

The plan starts from these locally verified facts:

- `purra` has no runtime dependencies and requires Python 3.11 or newer.
- The public complete-Run entry remains `purra.api.AgentCore.submit()`.
- Reactive execution is the default; Planned and Durable are explicit
  capabilities.
- Provider calls are opened in the canonical output journal before the Provider
  is invoked.
- Terminal Run state and canonical lifecycle output share a commit boundary.
- The current suite passes: `201 passed` on Python 3.11.15.
- A wheel built from a clean Git archive installs and passes
  `tests/installed_distribution_smoke.py`.
- Current source size is about 35,623 lines. The largest functions are
  `AgentRuntime.run()` (1,379 lines) and `AgentCore._execute_run()` (1,130
  lines).

Two counterexamples must become regression tests before implementation:

- Two Presets using the same component classes but different context source and
  compaction settings currently produce equal snapshots; delegation is absent
  from the snapshot.
- A nested tool property with an unknown JSON Schema `type` currently passes
  registration and runtime validation, allowing the handler to execute.

## 3. Non-negotiable design constraints

- Keep Core product-neutral. Do not add writing, screenplay, UI, transport,
  credential, Provider SDK, or database semantics.
- Keep Reactive as the default composition. Do not force Planner, TaskSpec,
  LongTask, Artifact, or Delegation into ordinary runs.
- Preserve one Root Run and one canonical event/output stream. Do not introduce
  child-Run orchestration.
- Preserve persist-before-publish, terminal atomicity, source-key idempotency,
  ordered cursors, approval fences, and cancellation behavior.
- Do not introspect arbitrary component object state. Opaque host configuration
  must be declared explicitly.
- Do not add a compatibility fallback that guesses missing `0.1` snapshot
  fields. Unprovable continuation must fail closed.
- Add no runtime dependency. Test/development dependencies require a separate,
  evidence-based decision.

## 4. Release strategy

This work targets `0.2.0`, not `0.1.x`, because it changes the supported
composition contract and intentionally rejects unsafe legacy continuation.

Implementation must use small, independently green commits in this order:

1. Add failing regression tests for the two verified defects.
2. Repair effective composition snapshots.
3. Repair tool-schema admission and runtime defense.
4. Tighten public exports and CI checks.
5. Refactor Engine orchestration without semantic changes.
6. Refactor Runtime orchestration without semantic changes.
7. Update English/Chinese documentation, changelog, and version metadata.

Do not mix correctness repairs with orchestration moves in the same commit.

## 5. Workstream A: effective Agent composition snapshot

### A1. Contract decision

Introduce snapshot schema version 2. It must describe the effective behavior
selected for a Run, rather than only the Python types of configured objects.

Use one small, host-declared component-binding contract for opaque components.
Each binding contains:

- a stable component id;
- a revision;
- an optional configuration digest when the revision alone is not authoritative.

`AgentPreset` owns these declarations. PurrA derives snapshots for its own
stateless built-ins and known immutable settings. It must not serialize
arbitrary `__dict__` values or call `repr()` as a fingerprint source.

An opaque configured component or factory without a binding is a composition
error. This applies to behavior-affecting context, compaction, execution-state,
planning, task-admission, and durable-dispatch components.

### A2. Delegation ownership

Move delegation capability policy into the resolved Agent composition:

- `None` means delegation is disabled.
- A `DelegationPolicy` means delegation is enabled and all policy limits are
  included in the snapshot.
- Delegation repository/executor instances remain Kernel infrastructure and are
  not serialized, but assembly must reject missing infrastructure for an
  enabled capability.
- Low-level non-Preset composition may retain explicit arguments, but it must
  produce the same effective snapshot semantics when durable continuation is
  used.

The delegation tool's model-visible schema and authorization contract must be
part of the effective enabled-tool snapshot.

### A3. Snapshot contents

Version 2 must cover at least:

- Preset id and revision;
- trusted prompt sections;
- context strategy;
- component bindings and known built-in configuration;
- compaction trigger and retention settings;
- planning enabled/disabled state and policy binding;
- task admission and durable dispatcher bindings;
- effective enabled tool schemas, policies, data/context contracts, and
  host-planned argument digest;
- delegation enabled state and all delegation limits;
- runtime limits and recovery policy.

Infrastructure identities, credentials, prompt bodies copied from untrusted
context, and arbitrary object state remain excluded.

### A4. Recovery behavior

- Persist `snapshotVersion: 2` in `run.started`.
- Compare the effective snapshot before any new model call, tool call, durable
  dispatch, or delegated execution.
- A version-1 or incomplete source snapshot cannot safely prove the old
  composition and must terminate continuation with a stable, explicit contract
  error.
- Do not silently upgrade an old snapshot by filling fields from the current
  process.
- New non-continuation runs remain available after the host supplies required
  bindings.

### A5. Required tests

- Same class plus different binding revision/digest produces different
  fingerprints.
- Changing compaction settings changes the fingerprint.
- Enabling delegation or changing any delegation limit changes the fingerprint.
- Missing binding for an opaque configured component fails during assembly.
- Snapshot serialization is deterministic and round-trips losslessly.
- Version-1/incomplete continuation fails before Provider, tool, or dispatcher
  invocation.
- Exact version-2 replay succeeds.
- Reactive Presets with only stateless built-ins remain minimal.

### A6. Expected files

- `src/purra/agent_presets.py`
- `src/purra/execution_profiles.py`
- `src/purra/engine/orchestrator.py`
- `src/purra/engine/options.py`
- `src/purra/delegation/policy.py`
- `tests/test_agent_presets.py`
- `tests/test_standalone_agent_conformance.py`
- `tests/test_second_host_conformance.py`
- `tests/test_task_orchestration_conformance.py`

Do not create a second snapshot hierarchy unless the existing
`AgentPresetSnapshot` cannot express version 2 cleanly.

## 6. Workstream B: recursive tool-schema admission

### B1. Supported schema subset

Define and document the exact JSON Schema subset enforced by Core. At minimum,
retain the behavior already claimed publicly:

- `type`: object, array, string, integer, number, boolean, null, or a non-empty
  list of these types;
- `properties`, `required`, `additionalProperties`, and `items`;
- `anyOf`, `oneOf`, `enum`, and `const`;
- `minLength`, `maxLength`, `minItems`, `maxItems`, `minimum`, and `maximum`;
- harmless annotation fields such as `title` and `description`.

Unsupported assertion keywords must be rejected at registration rather than
silently ignored. Annotation keywords may remain ignored after validation.

### B2. Composition-time validation

Add one recursive schema-contract validator at the existing
`inspect_tool_contract()` boundary. It must validate:

- supported type names and type-list shape;
- keyword value types;
- object/array child schema structure;
- `required` names and uniqueness;
- valid numeric/length bounds;
- nested `anyOf`/`oneOf` branches;
- unsupported assertion keywords.

Every catalog and `CoreToolExecutor` already passes through this boundary, so
do not add parallel validation in each caller.

### B3. Runtime defense

Runtime validation remains defense in depth:

- unknown schema types must return a violation, never `True`;
- malformed schema fragments must fail closed;
- the complete batch must still be rejected before any handler starts;
- rejected values must not be copied into diagnostics or public output.

### B4. Required tests

- Unknown nested `type` rejects catalog construction.
- Unsupported assertion keyword rejects catalog construction.
- Invalid type arrays, branch schemas, bounds, and `required` declarations are
  rejected.
- Every supported keyword has one positive and one negative focused case.
- End-to-end invalid input leaves handler-call count at zero.
- Add a built-in red-team case for schema fail-open and run the complete
  red-team catalogue from pytest.
- Existing Provider-stringified object/array normalization remains covered and
  cannot broaden the accepted schema.

### B5. Expected files

- `src/purra/tools/contract.py`
- `src/purra/tools/security.py`
- `src/purra/tools/executor.py` only if shared validation cannot remain at the
  existing boundary
- `src/purra/evaluation/security.py`
- `tests/test_model_tool_gateway_conformance.py`
- a focused `tests/test_tool_security.py` only if the conformance test becomes
  unreadable

## 7. Workstream C: public API and verification gates

### C1. Intentional exports

- Add explicit `__all__` declarations to supported public module roots.
- Remove accidental exports of imported modules, typing helpers, decorators,
  and standard-library names.
- Preserve intentionally documented symbols; any intentional removal belongs
  to `0.2.0` release notes.
- Add a boundary test asserting that exported values are explicitly listed and
  that module objects are exported only when deliberately documented.

Do not create a second manifest when the module-local `__all__` lists can be
the authority.

### C2. Test and CI changes

- Run the built-in security red-team catalogue in pytest.
- Add direct tests for the public evaluation and observability projections that
  make release decisions.
- Run CI on Python 3.11 and every newer Python version that the release claims
  to support.
- Keep wheel, sdist, clean-install smoke, and `git diff --check` gates.
- Measure coverage to locate untouched critical branches, but do not introduce
  an arbitrary repository-wide percentage threshold in this release.
- Defer a broad mypy/pyright rollout unless the hardening diff exposes a concrete
  type defect. Runtime validation and focused regression tests remain the first
  priority.

### C3. Expected files

- public package `__init__.py` files
- `tests/test_public_api.py`
- `tests/test_package_boundaries.py`
- focused evaluation/observability tests
- `.github/workflows/ci.yml`
- `pyproject.toml` only for version/classifier or justified test-tool changes

## 8. Workstream D: orchestration decomposition

Start only after Workstreams A-C are green. This phase changes ownership of no
state and introduces no new public API.

### D1. Engine

Reduce `AgentCore._execute_run()` to a readable lifecycle coordinator by
extracting its existing contiguous phases:

1. start Run and resolve per-Run factories;
2. reserve and build initial context;
3. plan and admit work;
4. build execution context and runtime inputs;
5. drive Runtime updates;
6. settle the terminal Run transaction.

Reuse the existing `context_phase`, `planning_phase`, `task_orchestration`, and
`durable_execution` modules. Add at most one private immutable phase-result
type where multiple return values otherwise become ambiguous.

### D2. Runtime

Reduce `AgentRuntime.run()` around its existing loop states:

1. prepare one logical Provider attempt;
2. execute and settle the Provider stream;
3. classify terminal model output;
4. authorize and execute one tool batch;
5. apply bounded recovery/replan decisions.

Keep one loop owner. Do not turn each phase into a service object or add a
plugin/event bus. A single private loop-state dataclass is acceptable if it
removes the current group of mutable local flags without hiding authority.

### D3. Measurable constraints

- `AgentCore._execute_run()` target: at most 450 lines.
- `AgentRuntime.run()` target: at most 500 lines.
- `AgentCore.__init__()` target: at most 200 lines.
- No extracted private function should exceed 300 lines.
- Replace the current file-only line caps with AST-based function caps while
  retaining the anti-backslide responsibility tests.
- No new internal import cycle.

These are ceilings, not reasons to split cohesive 20-line helpers into
one-line wrappers.

### D4. Behavior-preservation tests

The following paths must remain byte-for-byte or structurally equivalent at
their public boundaries:

- Reactive final response and public output order;
- Planned tool authorization and todo lineage;
- Durable handoff, continuation, leases, and idempotency;
- Provider interruption, truncation, and retry accounting;
- approval requested/resolved/canceled lifecycle;
- direct-live versus validated-result output;
- context compaction start/completion events;
- subscriber disconnect versus explicit Run cancellation;
- delegation within one Root Run;
- terminal projection failure and atomic rollback behavior.

## 9. Documentation and release work

- Correct the English and Chinese snapshot claims so they exactly describe
  version-2 behavior and the host binding obligation.
- Document the supported JSON Schema subset and rejection policy.
- Add a migration note: version-1 durable snapshots cannot be resumed under
  version 2 because their effective configuration cannot be proven.
- Update `CHANGELOG.md` with breaking changes and stable error codes.
- Bump package version to `0.2.0` only after all gates pass.
- Do not claim PyPI publication, real-Provider compatibility, or production
  multi-process durability without separate evidence.

## 10. Verification matrix

Minimum local gate:

```bash
python -m pytest
python -m compileall -q src
python -m build --sdist --wheel
python -m venv <temporary-smoke-venv>
<temporary-smoke-venv>/bin/python -m pip install --no-deps dist/*.whl
<temporary-smoke-venv>/bin/python tests/installed_distribution_smoke.py
git diff --check
```

Release evidence must record:

- Python versions exercised;
- total test count and skipped tests;
- security red-team totals;
- wheel/sdist and installed-smoke result;
- snapshot mismatch proof that no Provider/tool/dispatcher was called;
- invalid-schema proof that no handler was called;
- internal import-cycle count;
- remaining orchestrator function sizes;
- any unverified real-Provider or production-adapter limitation.

## 11. Rollback and failure handling

- Each workstream remains independently revertible.
- A failed snapshot migration must leave source Runs untouched and produce an
  explicit terminal/contract result; never rewrite historical snapshots in
  place.
- Schema admission changes happen before any handler execution, so rollback
  must not require data repair.
- If orchestration refactoring changes event order, persistence calls, retry
  counts, or cancellation ownership, revert that refactor commit rather than
  add a compatibility branch.

## 12. Explicitly deferred

- Provider SDK adapters inside Core;
- a production database implementation inside Core;
- child-Run trees or a second orchestration system;
- product/domain-specific planners, prompts, tools, or validators;
- automatic reflection of arbitrary component configuration;
- a plugin platform;
- broad lint/type/coverage tooling adopted without a demonstrated defect;
- performance optimization without a measured bottleneck.

These can be reconsidered only with evidence that the existing host ports and
focused hardening work are insufficient.
