# 从 0.x 升级到 1.0

[English](1.0.md)

本候选不承诺 0.x 别名、兼容编解码或自动迁移。不要原地切换正在执行的生产 Run。

1. 盘点 SDK／可选包版本、存储格式、调用回执、preset、模型／工具绑定和活跃 Run，保留备份及能读取原数据的环境。
2. 在旧运行时完成或明确取消活跃 Run，并对账外部效果。取消本地等待不等于远端效果已停止。
3. 在独立环境安装准确候选；优先使用新数据库。评估历史读取时使用可丢弃的备份副本，不把唯一生产数据交给验证脚本。
4. 分别验证历史读取和新 Run。重启宿主后检查新的持久 Run、用量和输出，保留回滚数据。

可选 PurrA SQLite 适配器默认使用 v4，显式启用持久审批后支持 v5，拒绝其他格式版本；Python 与 TypeScript 快照不能互换。启用前须检查就绪状态并排空未完成执行，见[离线升级与回滚流程](../../conformance/sqlite-upgrade.md)。此 v4→v5 路径不是通用的 0.x 应用迁移。

新的 invocation receipt 为 schema v3，TypeScript 状态导入拒绝不支持的回执版本。因此，适配器格式标记相同不等于 0.x 历史或活跃 checkpoint 一定兼容。本候选没有通用 0.x 历史迁移工具；选择新数据库也不授权删除旧数据。恢复诊断不授予 resume 权限。

自行实现持久化端口的宿主拥有自己的数据库结构和升级流程。可选适配器的 v4/v5 标记不代表所有宿主 SQLite 数据库的版本。应对照当前 Core 契约检查状态与事件的原子写入、预算记账、检查点和 lease 校验，不要向宿主自有表结构套用适配器格式激活工具。导入成功、函数参数匹配只是初步检查；修改应用依赖前，仍须用隔离的宿主测试数据验证实际行为。

未来 1.x 存储变更的发布说明必须分别声明历史读取、已验证的离线迁移和活跃 Run 续跑能力。可以明确要求排空活跃 Run，但不能静默遗弃任务和历史。迁移经过验证后才能声明支持。

## 已有规划事件存储的宿主

输出处理器除了完整 `planning.progress` 记录，还可能产生 `planning.delta` 预览。
如果宿主自有存储只允许前者，即使导入和函数参数都匹配，也可能拒绝新事件，导致规划 Run 失败。

宿主若继续采用完整记录展示，可在实际输出处理器构造处配置策略：

```python
class RecordPlanningProgressPolicy:
    async def authorize_provider_chunk(self, spec, chunk):
        return chunk

    async def authorize_planning_delta(self, spec, chunk):
        return None

processor = AgentOutputProcessor(repository, publisher,
                                 policy=RecordPlanningProgressPolicy())
```

此策略只关闭公开增量预览，保留完整规划进度、私有来源记录、预算记账和计划校验。
已有其他输出限制的宿主应在原策略上增加该决定，不要用此最小示例覆盖原限制；
使用输出处理器子类时，也须通过实际构造入口传入策略。

若要支持增量预览，则须完整接入作用域与尝试身份、活跃操作、已持久化原始片段、
事件预算、重放和 UI 处理；仅扩大事件白名单不充分。
以上两种选择均不允许绕过组合身份检查、直接续跑旧 Run。
