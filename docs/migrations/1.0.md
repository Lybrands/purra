# Upgrade from 0.x to 1.0

[简体中文](1.0.zh-CN.md)

There are no 0.x aliases, fallback codecs, or automatic migrations promised by
this candidate. Do not upgrade an active production Run in place.

1. Inventory the installed SDK and optional-package versions, storage formats,
   invocation receipts, presets, model/tool bindings, and active Runs. Retain a
   backup and an environment capable of reading the original data.
2. Finish or explicitly cancel active Runs in the old runtime and reconcile
   external effects. A canceled local wait does not prove a remote effect stopped.
3. Install the exact candidate in a separate environment. Start with a new
   database, or a disposable backup copy when assessing historical readability.
   Do not point a validation harness at the only production copy.
4. Check historical reads and new Run execution independently. Restart the host,
   verify a new persisted Run and its usage/output, and keep rollback data intact.

The optional PurrA SQLite adapter uses v4 by default and supports v5 after
explicit activation of durable approvals. Other format versions are rejected;
Python and TypeScript snapshots are not interchangeable. Inspect readiness and
drain unsettled execution before activating approvals. See the
[offline upgrade and rollback procedure](../../conformance/sqlite-upgrade.md).
This v4-to-v5 path is not a general 0.x application migration.

New invocation receipts use schema v3. TypeScript imports reject unsupported
receipt versions. Matching an adapter format marker alone therefore does not
establish that a 0.x history or active checkpoint is compatible.
No general 0.x history migration is supplied here; using a new database does not
authorize deleting the old one. Recovery inspection never grants resume authority.

Hosts implementing their own persistence ports own their database schema and
upgrade process. The optional adapter's v4/v5 marker does not describe every
SQLite database used by a host. Review that implementation's atomic state/event
writes, budget accounting, checkpoints and lease checks against current Core
contracts. Do not run adapter-format activation tools on unrelated host schemas.
Successful imports and matching callable signatures are only preliminary checks;
verify behavior with isolated host fixtures before changing application dependencies.

For future 1.x storage changes, release notes must distinguish historical reads,
validated offline migration, and continuation of active Runs. Requiring active
Runs to drain is explicit; silently discarding them or their history is not an
upgrade policy. Any migration must be verified before it is described as supported.

## Hosts with an existing planning-event store

The output processor can emit `planning.delta` previews as well as complete
`planning.progress` records. A custom repository that only allows the latter
will reject the new previews and can fail a planned Run despite successful
imports and matching method signatures.

A host retaining its existing complete-record presentation can supply an output
policy without changing storage authorization:

```python
class RecordPlanningProgressPolicy:
    async def authorize_provider_chunk(self, spec, chunk):
        return chunk

    async def authorize_planning_delta(self, spec, chunk):
        return None

processor = AgentOutputProcessor(repository, publisher,
                                 policy=RecordPlanningProgressPolicy())
```

This suppresses public delta previews, not complete planning progress, private
source records, budget accounting or plan validation. If the host already has
an output policy, add the delta decision to that policy instead of replacing its
other restrictions with this minimal example. Wire it through the host's actual
processor construction, including any processor subclass.

Supporting previews instead requires the host to implement the full event
contract: scope and attempt identity, active operation, exact persisted source
chunk, event budget, replay and UI handling. Merely widening an event allowlist
is insufficient. Neither choice authorizes resuming old Runs under a changed
composition without the usual identity checks.
